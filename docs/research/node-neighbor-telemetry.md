## What a table can show

Yes: capture directional radio observations, retaining which node measured each value. There are two different sources:

| Source | Measured by | Available signal | Meaning |
| --- | --- | --- | --- |
| Gateway packet receipt | G001 or G002 receiving a radio packet | Envelope `rx_snr` (dB), `rx_rssi` (dBm), when supplied | Signal on the final radio hop into that gateway |
| NeighborInfo report | Reporting repeater/gateway | Each neighbor's `node_id` and `snr` (dB) | Last remembered signal from a node heard by that reporter; no neighbor RSSI field |

Packet `from` remains the original source across relays. Therefore a member packet received at G001 through R001 measures R001→G001, **not** member→G001. Preserve hop metadata; `relay_node` is only the last byte of a node ID, so collisions/unknown values must remain unresolved. A supported zero-hop reception can identify the original sender as the direct neighbor. SNR and RSSI describe different quantities; neither alone proves delivery reliability. [Pinned packet and neighbor definitions](https://github.com/meshtastic/protobufs/blob/6b1ded439633cd03d4af85b44231b91d1d106278/meshtastic/mesh.proto), [current definitions](https://github.com/meshtastic/protobufs/blob/master/meshtastic/mesh.proto).

Suggested display columns: **Observer | Heard node | Original source | SNR (dB) | RSSI (dBm) | Direct/relayed/unknown | Report received | Measurement age | Source**. Show unavailable values as Unknown; leave RSSI unavailable for NeighborInfo. Use “Report received” rather than “Last heard” when the actual hearing time is absent. Keep gateway receipt rows distinct even when the underlying position/telemetry deduplicates.

Suggested storage is an append-only `link_observations` table with `observerDeviceId`, nullable `heardDeviceId`, `originalSourceNodeId`, nullable `snrDb`/`rssiDbm`, `sourceType`, `packetId` plus content identity, `reportReceivedAt`, nullable `observedAt`, `hopStart`, `hopLimit`, raw `relayNode`, identity-confidence/reason and private archive/receipt reference. Retain unknown raw node IDs without equating them to a verified device. For NeighborInfo also retain reporter ID, `last_sent_by_id` and reporter broadcast interval. A latest-per-direction view can summarize history; do not infer the reverse direction or a complete route.

Protobuf packet signal scalars lack explicit presence flags: a decoded zero can be an omitted default, while **0 dB SNR is a valid measurement**. Preserve available wire/provenance information and distinguish unknown presence from a confirmed zero; do not blindly discard zero SNR or assume every envelope has usable readings. NeighborInfo's per-neighbor hearing time and interval are defined for local storage and deliberately omitted by the pinned transmitter. Its report has no measurement timestamp: gateway radio receipt time and backend receipt time are separate evidence, neither establishes each neighbor's last hearing time. [Pinned generated packet schema](../../firmware/src/mesh/generated/meshtastic/mesh.pb.h), [pinned report construction](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/NeighborInfoModule.cpp#L55-L74).

## NeighborInfo constraints

- The module is optional, disabled by default and subject to build exclusion. It collects ordinary zero-hop packets even when the neighboring sender has not enabled it. NeighborInfo forwarding updates a full `last_sent_by_id`; preserve that distinction from the report owner. MQTT-originated packets are excluded from its neighbor collector. [Pinned module](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/NeighborInfoModule.cpp), [header](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/NeighborInfoModule.h), [module creation](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/Modules.cpp#L137-L141).
- Default recurring reports are **6 hours**, minimum **4 hours**, with at most **10 neighbors** in this build. Setting an interval below the minimum through admin resets it to the default. Reports are conditional, background traffic; airtime checks can suppress their LoRa transmission. They cannot provide the member GPS freshness measure. [Pinned defaults](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/Default.h#L29-L31), [admin enforcement](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/AdminModule.cpp#L987-L995), [neighbor limit](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/NeighborInfoModule.h#L3).
- By default the report stays off LoRa and goes to local app/MQTT paths. A directly connected gateway can export its own report without radio broadcast. An isolated RAK needs `transmit_over_lora` enabled to export its observations through a gateway. This is restricted on the default public channel and checked against airtime. The gateway and forwarding path must accept NeighborInfo: the pinned receive path skips these packets when its module is disabled; `CORE_PORTNUMS_ONLY` also rejects them. MQTT/channel uplink, encryption and sender opt-in gates still apply. [Official module documentation](https://meshtastic.org/docs/configuration/module/neighbor-info/), [pinned receive filters](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/Router.cpp), [MQTT uplink](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mqtt/MQTT.cpp#L766-L842).
- Project “repeater” is a function, not a requirement to choose firmware `REPEATER`. R001/R002/R003 use visible `ROUTER` profiles. The pinned role definition marks `REPEATER` deprecated and describes it as originating no telemetry/other packets. Do not switch roles for this feature; verify actual config and module availability. [Existing profile](../operations/rak-pilot-setup.md), [pinned role definitions](../../firmware/src/mesh/generated/meshtastic/config.pb.h), [official roles](https://meshtastic.org/docs/configuration/radio/device/).

## Other useful data

| Data | Availability and useful interpretation |
| --- | --- |
| Device health | `DeviceMetrics`: voltage, reported battery level, uptime, channel utilization and transmit airtime. Level 101 means external power/charging/no battery, not 101% charge. Uptime drops can suggest restart; voltage/charge remain hardware-dependent. |
| Radio diagnostics | `LocalStats`: received/transmitted/bad/duplicate/relayed/dropped packets, relay cancellations, node counts, heap and noise floor where supported. Default periodic delivery is to the local app; request replies are possible, so do not promise automatic MQTT delivery. Counters reset on reboot; they do not directly measure end-to-end member packet loss. |
| GPS context | Altitude, speed/course, fix quality/type, dilution and satellite count when actually populated and transmitted. Preserve GPS measurement time independently of reception. |
| Fitted sensors | Temperature/humidity, pressure, power-channel voltage/current and detection events where hardware, drivers and module configuration support them. Battery voltage alone does not measure solar production or charge current. R003 temperature/humidity is verified; other sensor availability must follow inventory/evidence. |

Sources: pinned [DeviceTelemetry implementation](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/Telemetry/DeviceTelemetry.cpp), [telemetry schema](../../firmware/src/mesh/generated/meshtastic/telemetry.pb.h), [current telemetry schema](https://github.com/meshtastic/protobufs/blob/master/meshtastic/telemetry.proto), [position schema](../../firmware/src/mesh/generated/meshtastic/mesh.pb.h), [measured infrastructure reports](../operations/repeater-telemetry.md).

## Current capture and next useful step

The worker already archives exact received MQTT payloads and receipt metadata privately **before** filtering. Unsupported ports and fields can therefore be interpreted later if their packets actually reached the subscribed/authorized broker subtree. The adapter currently normalizes member positions, battery voltage and infrastructure temperature/humidity; it drops signal metadata from normalized receipts and does not decode NeighborInfo or LocalStats. Archiving does not create missing radio reports or bypass the broker ACL. [Worker](../../backend/mqtt_worker.py), [adapter](../../backend/mqtt_adapter.py), [archive operations](../operations/live-mqtt.md#raw-mqtt-archive--2026-10-15).

Proposed first implementation: extract existing gateway signal metadata into per-gateway receipt/link observations, with direct/relayed/unknown labels and explicit missing values, using archived/live data without changing node settings. Then, if repeater-side views are wanted, separately verify/enable NeighborInfo across the required radio path and confirm real delivery/cadence before filling repeater rows. No live archive inspection, setting readback, hardware test or table implementation was performed in this research.

The first passive phase is now implemented in `snorr/rak-survey`; [source, checks and rollout boundary](../operations/rak-neighbor-signals.md). The proposal below remains the original research context. Hardware flashing, gateway delivery and portal decoding of the new companion report remain unverified/separate follow-ups.

**Yes.** A small infrastructure collector/exporter could better serve placement and tracking diagnostics while keeping standard GPS and NeighborInfo messages intact. This is a proposal, not implemented firmware; reconcile with the fork's newer branch before coding.

First phase: passively collect **verified direct receptions** already reaching the module, storing observer/full neighbor ID, latest RSSI/SNR with presence, monotonic last-heard age and optional bounded window count/mean. The SX126x driver already populates both radio values; the existing collector already stores hearing time but exports only SNR. Keep reporting cadence separate from neighbor expiration, so a slow summary does not imply a recently heard link. [Radio values](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/SX126xInterface.cpp#L288-L302), [collector](../../firmware/src/modules/NeighborInfoModule.cpp).

Make local capacity configurable and bounded: **32 entries** is a candidate for roughly 20 members plus infrastructure, subject to RAM checks. Separate this from a conservative per-packet row/byte cap, rotating/coalescing batches with snapshot identifiers and explicit truncation/completeness. The existing standard packet cap remains ten; a missing batch/omitted row must not erase a known link or imply failure.

Candidate bench intervals: **30–60 seconds for gateway MQTT-only summaries**, **5–15 minutes for repeater LoRa summaries**, with jitter, change coalescing, capped packet size and airtime deferral. These are starting hypotheses, not measured capacity. Keep GPS ahead of background diagnostics; measure receipt gaps, airtime and runtime. The standard four-hour clamp exists in both admin handling and startup normalization; use a separate custom schedule/configuration rather than assuming changing one timer removes it. Gateway export can remain MQTT-only with `CLIENT_MUTE`/radio silence retained; that role prevents rebroadcasting, not local processing. [Normalization](../../firmware/src/mesh/NodeDB.cpp), [mute behavior](../../firmware/src/mesh/FloodingRouter.cpp), [MQTT before radio send](../../firmware/src/mesh/Router.cpp).

Preserve standard port 71/schema; use a versioned companion payload on an available private port in **256–511** for extra fields. Do not repurpose the standard local-only neighbor timestamp. Adding new protobuf field numbers can be wire-compatible, but requires regenerated bindings and size checks; stock NeighborInfo handlers decode and re-encode using their known schema, so cannot be assumed to preserve extensions. Private-port traffic still needs permitted forwarding/uplink. [Port allocation](https://github.com/meshtastic/protobufs/blob/6b1ded439633cd03d4af85b44231b91d1d106278/meshtastic/portnums.proto), [protobuf compatibility](https://protobuf.dev/programming-guides/proto3/#updating), [re-encoding](../../firmware/src/mesh/ProtobufModule.h).

Scope limit: modules run **after duplicate filtering**, so initial counts mean accepted observations, not every RF reception, delivery percentage or complete repeater-to-repeater topology. Capturing duplicates needs a later bounded receive observer before that filter; identifying arbitrary relay transmitters still faces the one-byte ID ambiguity. None of these summaries replaces GPS age or proves current reachability. [Receive filtering](../../firmware/src/mesh/Router.cpp), [duplicate handling](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/FloodingRouter.cpp#L28-L64).

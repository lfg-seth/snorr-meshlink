# Meshtastic monitoring and recording projects

Research date: **2026-10-16**. Planning evidence for **Check Meshtastic monitoring and recording stacks for the pilot**; no software was installed or live configuration changed. Repository source snapshots were downloaded into `/tmp` for inspection, without executing their code. Compatibility below is source-supported, not a successful test against SNORR traffic.

## Finding

**MeshMonitor is the strongest turnkey trial candidate for the current setup.** Its current version can consume encrypted Meshtastic MQTT over TLS without a radio, offers a subscribe-only mode, stores telemetry/history, exports Prometheus metrics, supplies a Grafana dashboard and has a Proxmox LXC template. **tcivie/meshtastic-metrics-exporter** is the strongest smaller MQTT→SQL→Grafana template when detailed time-series dashboards are the priority. Neither should replace the existing portal worker or its raw archive without deliberate compatibility and retention work.

Several plausible search results are misleading for this deployment: a prominent Prometheus exporter skips encrypted packets, two packet analyzers do not wire TLS into their inspected MQTT clients, and the similarly named `meshtastic-mqtt` translator explicitly supports only old v1.2 firmware. Details and pinned primary sources follow.

## Existing SNORR constraints

The current [MQTT operations record](../operations/live-mqtt.md) describes public TLS `mqtt.snorr.org:8883`, encrypted protobuf `ServiceEnvelope` traffic and two V3 uplinks. The worker subscribes to `snorr/pilot/#`, but the documented broker ACL grants only `snorr/pilot/2/e/#`. A broader subscription does not expand its access. A monitoring consumer should have its own read-only credential/client ID and use that narrower subtree unless the broker administrator authorizes another scope.

The Python worker already archives exact received MQTT bytes plus receipt metadata into private PocketBase `mqtt_archive` before normalization, including malformed/unsupported traffic and separate gateway copies. It preserves independent gateway receipts while deduplicating displayed GPS using source, packet ID and content. It has no automatic pruning. Preserve that record and the portal's 15-minute GPS-measurement-age stale rule; generic last-heard/node-online indicators do not establish fresh GPS. Monitoring cannot recover radio/broker deliveries missed before collection or provide field viewing when internet backhaul fails.

The [portal LXC record](../operations/portal-lxc.md) reports Ubuntu 24.04, 4 logical CPUs, 8 GiB RAM and a 64 GiB disk allocation. **Available headroom was not measured in this research.** No new radio or paid service is inherently required for an MQTT-only trial. Docker availability/nesting inside the existing LXC and a separate LXC allocation are unverified; do not assume the current container is ready for either supplied template.

## 1. MeshMonitor: best turnkey trial

Current [MQTT bridge documentation](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/docs/features/mqtt-broker.md) documents `mqtts://…:8883`, wildcard subscriptions, authentication, inbound ServiceEnvelope ingestion and a **standalone** bridge with no parent broker. Set its mode to **`subscribe_only`**: documentation says upstream publishes are refused. Keep it unlinked from physical node sources. The [setup guide](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/docs/features/mqtt-setups.md) explicitly describes monitoring without a radio. The [Channel Database](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/docs/features/channel-database.md) accepts base64 PSKs and performs server-side decryption; the private pilot name/key must be entered privately. Exported channel lists include full PSKs and must stay out of Git/log bundles.

It supplies a [Grafana mesh-health dashboard and authenticated Prometheus scrape example](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/examples/grafana/README.md), covering utilization, voltage/battery/SNR, liveness, messages and source state. It is an app plus a metrics endpoint; Prometheus and Grafana still need hosting/configuration. The example dashboard shows nodes heard within 30 minutes, while the endpoint's default export window is 24 hours. Neither matches the portal's GPS freshness rule automatically. Example airtime/battery thresholds are upstream defaults, not validated SNORR limits.

**History and two-gateway behavior:** [ingestion source](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/src/server/mqttIngestion.ts) deduplicates text rows by source+sender+packet ID; do not generalize that to GPS or every packet type. The [MQTT packet log service](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/src/server/services/mqttPacketLogService.ts) builds a row for each gateway reception with gateway ID, topic, receipt time and RF metadata. Logging requires enabling its setting. Its default cap is **5,000 rows per source and 24 hours**, cleaned every 15 minutes. Rows contain summaries and bounded previews, not the exact raw MQTT payload. The bridge's 60-second topic+packet-ID echo suppression prevents loops; it is not proof of correct source+content GPS dedup across two gateway topics. An actual paired-gateway fixture trial is required.

**Template maturity:** [Docker compose](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/docker-compose.yml), [Proxmox LXC template build/update documentation](https://github.com/Yeraze/meshmonitor/blob/cc0a572d0c7f00245a5aba0c9102e0f859db8dec/lxc/README.md) and supplied dashboard are concrete starting points. The LXC template is a separate Debian-based environment, not an installer to run over the production Ubuntu portal container. Its broader messaging, automation, broker and proxy features are unnecessary for this trial. Recommendation is an isolated read-only evaluation, not replacement of the current portal.

## 2. tcivie exporter: most direct SQL/Grafana template

The [Compose stack](https://github.com/tcivie/meshtastic-metrics-exporter/blob/1881f614a42b3b377e38f8c54c4ebb52835c8eec/docker-compose.yml) contains the Python MQTT consumer, TimescaleDB/Postgres and Grafana with provisioned dashboards. [Consumer source](https://github.com/tcivie/meshtastic-metrics-exporter/blob/1881f614a42b3b377e38f8c54c4ebb52835c8eec/main.py) enables a default TLS context with `MQTT_IS_TLS=true`, supports configurable host/port/topic/login, and parses ServiceEnvelope. [Processor source](https://github.com/tcivie/meshtastic-metrics-exporter/blob/1881f614a42b3b377e38f8c54c4ebb52835c8eec/exporter/processor/processor_base.py) takes `MQTT_SERVER_KEY` as base64 AES key, so a full private pilot PSK is configurable despite README language referring to the default channel. Only one configured PSK is tried. Matching real firmware packets remains untested.

It stores normalized telemetry/position/packet metadata and Grafana queries SQL; it no longer needs Prometheus for this path. It does **not** archive every original MQTT envelope. The consumer deduplicates solely on `packet.id` before decoding, dropping second-gateway copies and risking collisions across senders. The former per-gateway accounting hook is explicitly a no-op. [Database initialization](https://github.com/tcivie/meshtastic-metrics-exporter/blob/1881f614a42b3b377e38f8c54c4ebb52835c8eec/docker/timescaledb/init.sql) expires dedup IDs after five minutes via a scheduled job and drops metrics older than 30 days; this is incompatible with treating it as the pilot's no-prune evidence archive.

Before a trial, fix development defaults in Compose: published Postgres port, `postgres/postgres`, externally bound Grafana, moving `latest-pg16` image and sample configuration. Preserve the existing archive separately. Choose this option if SQL history and supplied investigation dashboards justify maintaining another database; it is less suitable for authoritative multi-gateway reception analysis without changes.

## 3. MeshView: packet and gateway history

[MQTT reader source](https://github.com/pablorevilla-meshtastic/meshview/blob/424998090dd98a1fb9a842f912f15df8c07ba76e/meshview/mqtt_reader.py) accepts ServiceEnvelope and supports configured secondary PSKs, including full 16/32-byte keys. However, its inspected `aiomqtt.Client` call passes host/port/login without a TLS context/options: merely setting port 8883 is insufficient. A reviewed TLS patch or private local TLS tunnel would be needed; do not downgrade the public broker transport. This reader also logs decoded secondary keys at startup, a concrete secret-redaction issue to fix before providing the private pilot PSK.

[Storage source](https://github.com/pablorevilla-meshtastic/meshview/blob/424998090dd98a1fb9a842f912f15df8c07ba76e/meshview/mqtt_store.py) keeps one Packet keyed only by radio packet ID and PacketSeen records by packet ID+gateway+rx_time, preserving distinct receiver RSSI/SNR/hops. The packet-ID-only identity can conflate senders/reused IDs. It stores a serialized packet **after decryption**, not each exact original MQTT envelope, and skips malformed/undecryptable messages. [Docker documentation](https://github.com/pablorevilla-meshtastic/meshview/blob/424998090dd98a1fb9a842f912f15df8c07ba76e/README-Docker.md) provides GHCR image, persistent volumes and SQLite/Postgres support. [Sample cleanup settings](https://github.com/pablorevilla-meshtastic/meshview/blob/424998090dd98a1fb9a842f912f15df8c07ba76e/sample.config.ini) include a 14-day keep period; review activation/retention before use. Useful diagnostic UI, but more adaptation than MeshMonitor for the present TLS endpoint.

## 4. Malla: archive/exploration alternative

[Capture source](https://github.com/zenitraM/malla/blob/7c3827510cb9e6454059764276faabe2c334bc58/src/malla/mqtt_capture.py) tries multiple configurable channel keys, stores `raw_service_envelope` blobs and gateway/topic metadata into SQLite, and inserts each arrival rather than globally discarding another gateway's copy. It can keep malformed protobuf receipts, but intentionally skips JSON and drops oversized payloads before storage, so its archive is narrower than SNORR's exact all-delivery archive. Raw packet counts include duplicate radio reports; unique transmissions need an explicit query/identity policy.

The same inspected client setup calls `connect()` without `tls_set`/TLS context; current direct TLS compatibility is absent in this snapshot. [README configuration](https://github.com/zenitraM/malla/blob/7c3827510cb9e6454059764276faabe2c334bc58/README.md) supplies Docker, Gunicorn, config/env support and default retention **0 = never delete**. It includes packet browser, maps, gateway comparison and analytics, rather than a supplied Grafana stack. Native Python requires 3.13+, differing from production's recorded 3.12. Worth considering for exploration only after a TLS change; avoid maintaining another full packet database unless its UI provides needed value.

## Other names that arise in searches

- **hacktegic Prometheus exporter:** [intake source](https://github.com/hacktegic/meshtastic-prometheus-exporter/blob/856471e44b9d456e77d5fea11ac8834976e8bfc7/src/meshtastic_prometheus_exporter/__main__.py) supports MQTT TLS and local serial/TCP/BLE but explicitly skips `encrypted` packets. It therefore does not directly consume the current encrypted feed. Its apparent dedup uses `cache.setdefault(id, True)` followed by `if not unique`; repeated entries remain True, so source inspection indicates suppression is ineffective. This finding was not runtime-tested. Prometheus history is metrics history, not a raw packet archive. [Compose](https://github.com/hacktegic/meshtastic-prometheus-exporter/blob/856471e44b9d456e77d5fea11ac8834976e8bfc7/docker-compose.yml) and dashboard assets remain useful references.
- **cordelster mesh-metrics:** [README](https://github.com/cordelster/mesh-metrics/blob/ce2258ce4ec475f0b79d4577845959a86ba4f5e3/README.md) and [daemon source](https://github.com/cordelster/mesh-metrics/blob/ce2258ce4ec475f0b79d4577845959a86ba4f5e3/scripts/meshmetricsd.py) show serial/IP client polling with telemetry request packets and Prometheus textfile/HTTP output. It can work without internet but is not a passive MQTT recorder. A field-local monitoring design could revisit it deliberately, including airtime/power effects.
- **joshpirihi/meshtastic-mqtt:** [pinned README](https://github.com/joshpirihi/meshtastic-mqtt/blob/a1d61a72abf7c1b4942d34b0de099d842d065134/README.md) explicitly limits it to old v1.2 firmware and decrypted packets. Latest default-branch commit was **2023-03-01**; GitHub reports no detected license. Its Traccar/plain-MQTT translation role is not a current monitoring template for the pilot.
- **Meshlog:** the [project's own page](https://meshlog.camal.eu/) asks the user to select a raw debug `.txt` log for offline parsing. It is useful for log-to-map investigation, not evidence of a persistent encrypted-MQTT/Grafana monitoring stack. Do not confuse it with MeshView or unrelated projects named Meshlog.
- **JSON MQTT templates:** [beegee-tokyo's Meshtastic-Sensor-Network](https://github.com/beegee-tokyo/Meshtastic-Sensor-Network) supplies Node-RED sensor parsing for InfluxDB/Grafana but expects JSON and an existing installed backend. It does not directly fit this encrypted protobuf subtree. The official [module schema](https://github.com/meshtastic/protobufs/blob/master/meshtastic/module_config.proto) now marks JSON MQTT deprecated/ignored since firmware 2.8.0; the pilot remains pinned to 2.7.26. Avoid building a new dependency on this legacy format.

## Trial requirements before adoption

Use an isolated instance, a separate read-only MQTT identity, certificate/hostname-verified TLS and the full pilot PSK held privately. Pin an actual released image/commit; the inspected `main` snapshots are evidence, not chosen production releases. Bind UI/metrics privately, require authenticated access and disable publishing/radio links. No additional public hostname or outreach is authorized by this note.

Replay sanitized or privately held paired-gateway fixtures to check one source transmission versus two gateway receipts, packet-ID reuse by different senders and changed payloads, wrong-key/unknown-port/malformed data, zero/missing signal values and distinct GPS/radio/receipt timestamps. Then verify with actual authorized read-only traffic. Count reception and unique-transmission metrics separately. Check that telemetry activity does not refresh a stale GPS fix and that MQTT loss ages the existing fix rather than implying current field visibility.

Measure RAM/CPU, disk growth per day including indexes/backups and query cost on representative traffic before deciding cohosting/retention. Keep pilot evidence archival rules separate from shorter metrics/log retention. Verify restart persistence, restricted credentials, a private backup and isolated restore. A working app page or a recent MQTT message alone does not verify fresh GPS, gateway availability, field coverage or offline operation. These are proposed acceptance checks, not measured results.

## What the GPS-related customization actually does

The ahead commits do **not** modify the GPS driver, `PositionModule`, position protobufs, measurement timestamps, or movement-detection implementation. They configure existing GPS/smart-broadcast behavior and customize **MQTT map reports**, plus general network defaults. There is no new autonomous GPS engine to transplant. This conclusion is scoped to these 17 commits and the net comparison, not all historical upstream work.

At fork head, active `userPrefs.jsonc` defaults enable GPS and smart position reporting, set GPS acquisition to **600 seconds**, position broadcast to **1,800 seconds**, and device telemetry to **600 seconds**. A 30-minute periodic broadcast cannot meet the agreed 15-minute position-age target for a stationary member; movement-triggered reports do not establish a stationary guarantee. Acquisition, transmission, actual delivery, and measurement age still need separate testing. The SNORR channel/full-precision entries are commented examples, not active defaults. [Pinned preferences](https://github.com/lfg-seth/firmware/blob/76d5156e72d9d9aaa9722b7bbc1336335b685984/userPrefs.jsonc).

The substantive map change forces map precision to **32**, bypasses the former **12–15** validation, and changes the default map interval from one hour to ten minutes. These are the publishing node's own `MapReport` settings; they do not implement dispatch aggregation of all received member positions or alter normal member `POSITION_APP` reporting. [Pinned MQTT implementation](https://github.com/lfg-seth/firmware/blob/76d5156e72d9d9aaa9722b7bbc1336335b685984/src/mqtt/MQTT.cpp), [header](https://github.com/lfg-seth/firmware/blob/76d5156e72d9d9aaa9722b7bbc1336335b685984/src/mqtt/MQTT.h).

**Source-level defect to avoid carrying forward:** map-report coordinate encoding still adds `1 << (31 - map_position_precision)` to latitude and longitude. At precision 32, the unsigned precision arithmetic underflows the shift count; shifting by that amount is undefined C++ behavior. Setting the precision field to 32 therefore does not prove correct full-precision coordinates. A full-precision path would need an explicit safe case, or dispatch should ingest ordinary position packets. This is static reasoning from the pinned source, not a reproduced runtime failure. [Coordinate encoding](https://github.com/lfg-seth/firmware/blob/76d5156e72d9d9aaa9722b7bbc1336335b685984/src/mqtt/MQTT.cpp).

## What survives and what current upstream already provides

Net fork changes are limited to `Default.h`, `MQTT.cpp`, `MQTT.h`, `userPrefs.jsonc`, the RAK4631 RGB definition, a commented environmental example, `logo.png`, and `rak4631.uf2`. GPS diagnostic/flasher programs and forced environmental telemetry do not survive. [Net comparison](https://github.com/lfg-seth/firmware/compare/f1aefc4eef47c3f1f41eb2221f788b20c77ff50a...76d5156e72d9d9aaa9722b7bbc1336335b685984).

Pinned current upstream still exposes the same GPS/smart-position preferences, still defaults map precision14 and validates12–15, retains hour-scale map/node/neighbor constraints, and enables RAK4631 `HAS_NCP5623`. Thus the fork-specific map/default/RGB overrides are not literally present in the inspected current files. GPS timing configuration already exists upstream; there is no fork GPS algorithm to classify as subsequently merged. This is a targeted source comparison, not patch-equivalence analysis of all 1,887 later commits. [Current preferences](https://github.com/meshtastic/firmware/blob/b48e1e0a2f591631f0b7a9ccad3ab7a3e4791b5f/userPrefs.jsonc), [defaults](https://github.com/meshtastic/firmware/blob/b48e1e0a2f591631f0b7a9ccad3ab7a3e4791b5f/src/mesh/Default.h), [MQTT](https://github.com/meshtastic/firmware/blob/b48e1e0a2f591631f0b7a9ccad3ab7a3e4791b5f/src/mqtt/MQTT.cpp), [RAK variant](https://github.com/meshtastic/firmware/blob/b48e1e0a2f591631f0b7a9ccad3ab7a3e4791b5f/variants/nrf52840/rak4631/variant.h).

## Pilot implications

Project inference from inspected source and agreed requirements:

1. Preserve the intent: accurate member positions, controllable acquisition/report frequency, predictable provisioning. Evaluate these on a selected current upstream release, and port a specific missing behavior only after measuring it. The old fork's 30-minute broadcast preference and broad extra telemetry traffic should not become pilot defaults unchanged.
2. For dispatch, evaluate received ordinary position packets with original GPS measurement time; reducing a publishing gateway's own map-report interval does not solve member freshness. Test stationary/moving tracking, fresh-fix validity, power-on operation without a phone, 15-minute age visibility, and 4-hour minimum/12-hour target runtime on the six planned GPS V4s.
3. RAK relays need their exact cores/sensors identified before deciding whether the RGB-controller override remains useful. Additional node/neighbor broadcasts consume airtime; their value should be justified against member-location delivery.
4. No ahead commit implements strictly LoRa receive-only V3 internet gateways, multi-backhaul dispatch deduplication, age handling, a local command-post viewer, or offline companion-app behavior. These need explicit configuration/integration checks. The accepted requirement is local positions at command post and on capable members' companion apps while both internet backhauls are unavailable; background maps and radio-delivered positions must be tested separately.
5. Public fork history includes broker credentials and example channel-key material. Do not reuse them for the private pilot or copy values into this repository; provision fresh secrets through ignored private/local data. Their present validity and use are unknown.

No firmware was built, scripts executed, boards flashed, credentials used, RF settings approved, or hardware/coverage/battery/internet-outage tests performed. No SnorrMesh remote was added or history changed.

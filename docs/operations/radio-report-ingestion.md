# RAK neighbor and sensor power ingestion

2026-10-16 Pacific. The owner requests database/portal support for the flashed RAK neighbor firmware and INA219 sensors. Source implements normalization, an additive migration and display in the existing Infrastructure table, map relationships and node cards. Deployment evidence is recorded below after release verification.

## Data contract

- The encrypted private-channel adapter recognizes `SNNS` v1 on private port 256. It checks exact header/row lengths, version/reserved flags, reporter/sender agreement, row/total counts, bounded hearing ages, unique non-self node IDs, nonzero counts and valid RSSI/quarter-dB SNR. Other private applications remain unsupported. SNNS zero SNR and zero hearing age are valid.
- `neighbors` ingestion stores one private `neighbor_reports` record per source/content packet key, with a unique index, and its directional `link_observations` in the same transaction. All gateway receipts remain in `packet_receipts` and the original MQTT archive. A second gateway or replay cannot add another report or set of links, including for an empty standard report.
- Each SNNS row identifies the reporting receiver, full heard radio ID, mapped device when known, RSSI/SNR, hearing age at encoding, accepted observation count, boot ID, sequence, reporter uptime, subset/capacity flags and first transport gateway. Unknown radio IDs remain visible in the table; maps require known endpoints/locations. The original source of the traffic heard by the RAK is unknown. These rows describe a direct observation at the RAK, independently of the report's path to the gateway.
- Hearing age is not an absolute timestamp. Store `observedAt = null`; never subtract age from MQTT receipt to invent a last-heard clock. UI labels the age as **at report**, excluding transport delay. Within a reporter's boot, a delayed lower sequence cannot replace a newer relationship reading. Across boots, absolute chronology remains unknown. Missing/partial rows never delete relationships or establish link failure.
- Standard `NeighborInfo` reports are supported with matching reporter provenance and at most 32 neighbors. RSSI, absolute hearing time and observation count stay unknown. Non-optional scalar SNR zero is ambiguous when omitted on the wire, so it stays unknown; SNNS has explicit fixed-width zero values.
- Infrastructure `PowerMetrics` channels 1–8 preserve independently present `powerNVoltage` (V) and `powerNCurrentMa` (signed mA). Legacy environment voltage/current use separate `sensorVoltage` / `sensorCurrentMa`. Zero is valid; absent fields never become zero. Neither source overwrites device battery voltage, solar readings or the existing battery-current interpretation. These observations are accepted even before a declared capability is configured, without enabling health rules.
- Each power metric retains measurement/receipt clocks separately. Unknown, delayed and future measurements cannot displace a newer valid reading. Future is evaluated against original receipt time, including during historical replay. The UI shows channel/source and stale/unknown timing. Wiring, current polarity, calibration and charger/load accounting remain unverified; the UI does not interpret the raw sign as battery charging/discharging.

The source of record is the pinned firmware's [`SnorrNeighborSignals.h`](../../firmware/src/modules/SnorrNeighborSignals.h), [`INA219Sensor.cpp`](../../firmware/src/modules/Telemetry/Sensor/INA219Sensor.cpp) and [`telemetry.proto`](../../firmware/protobufs/meshtastic/telemetry.proto). The INA219 driver writes legacy environment union members even when PowerMetrics is selected; observed channel 3 is retained literally. No channel remapping or firmware fix is hidden in the portal. [Official telemetry configuration](https://meshtastic.org/docs/configuration/module/telemetry/) distinguishes sensor power reporting from device battery voltage. Private channel encryption does not cryptographically authenticate these reports.

## Archive recovery

`backend/replay_radio_archive.py` reads a private SQLite archive through a read-only connection. Default is dry-run; `--apply --credentials PATH` uses the normal worker-only validation route. `--through` requires an explicit inclusive original-receipt UTC cutoff with milliseconds. Run against an isolated database copy first and take a full verified backup before live application.

Only newly supported neighbor/power data is replayed. Original bytes, archive decode outcomes and receipt/measurement clocks stay intact. Power-only supplements append `:power-v1` to the stable packet key, because older environment observations may already occupy the original key; they do not replace prior observations. Repeat application deduplicates records, while retaining retry receipts. The script reads the current verified source mapping; do not use it across an unrecorded device-ID reassignment. It prints aggregate counts only.

## Verification

Initial staged checks pass: 57 backend integration checks, 45 frontend checks, TypeScript and live production build on the existing LXC's pinned Node/runtime. Local decoder-only tests also pass; the local Windows environment lacks frontend dependencies and unrestricted temp/socket access, so full verification uses disposable server databases.

An isolated online SQLite copy preserves all nine live device identities/configuration, accounts, assignments, positions and archived payloads through migration/replay. The snapshot has 1,570 MQTT receipts: 11 SNNS reports and nine power-bearing packets become 15 directional rows and nine power supplements. A second replay accepts zero new records and reports 20 duplicates. SQLite integrity passes. Only G001 is represented; this does not verify fresh G002 delivery.

The copy exposes R004 channel 3 around 0.008 V / +1.7 mA and separate legacy environment readings; R005 channel 3 around 4.204 V / −322.6 mA and separate environment readings. These are reported samples at their original times, not calibrated measurements or a verified simultaneous power balance. No hardware, radio profile, sensor calibration, site installation, runtime or field coverage changes are included.
